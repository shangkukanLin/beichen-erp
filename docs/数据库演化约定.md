# 数据库演化约定（2026-09-30 起）

> 背景：项目**尚未上线**，不存在"老库需要就地升级"的场景。此前表结构由**两条路径**共同构成 ——
> `schema.sql`（`CREATE TABLE IF NOT EXISTS`）**加** `DataInitializer` 里的 18 个 `migrate*()` 启动期 `ALTER`。
> 经核查：全新库仅靠 `schema.sql` 会**缺 105 列**（32 张单据表的操作人四列等），也就是说"全新安装能跑"
> 其实依赖了那条启动迁移。本次已把 DDL 全部归位到 `schema.sql`，并**删除全部启动期迁移代码**。

## 一、唯一事实来源

| 环境 | 表结构来源 | 说明 |
|---|---|---|
| **未上线期（当前）** | **`beichen-erp-server/src/main/resources/schema.sql`** | 全 `CREATE TABLE IF NOT EXISTS`（幂等）；启动由 Spring `sql.init` 执行（`mode: ${SQL_INIT_MODE:always}`） |
| 上线后（建议） | **Flyway** | `V1__base.sql` = 现 `schema.sql`；此后每次变更一个 `V<n>__xxx.sql`；生产设 `SQL_INIT_MODE=never` 交由 Flyway |

**硬性要求**：应用代码里**不得**再出现 `ALTER TABLE` / `CREATE TABLE` / 补列逻辑（含 `information_schema` 判存在后 DDL）。
缺表缺列的后果由启动门禁统一暴露。

## 二、启动门禁（`DataInitializer.assertSchemaReady()`）

启动最早阶段（`@PostConstruct`，早于端口放行）校验必需表/列，缺失即 `IllegalStateException` 让应用**起不来**：

- 基础表/列：`sys_company/sys_role/sys_menu/sys_user/...`、`material_type`、`dev_phase_template`、
  `outsource_contract_template`、`screen_model`
- 配置列：`sys_menu.customized`、`sys_role.customized_menu`、`sys_role_menu_plan.menu_id`
- **单据操作人四列（32 张表 × 4 = 128 项）**：`create_by`/`create_by_name`（`MetaObjectHandler` 自动填充）、
  `auditor_id`/`auditor_name`（审核盖章）—— 表清单见 `DataInitializer.DOC_TABLES`

## 三、加/改一个字段的标准动作（未上线期）

1. 改 `schema.sql` 里对应表的 `CREATE TABLE` 块（**不要**写 `ALTER`，保持整表可重放）
2. 若该列属于"必须存在"的范畴，把它加进 `assertSchemaReady()` 的清单（或 `DOC_TABLES` 这类分组常量）
3. **重建数据库**：`DROP DATABASE beichen_erp; ` 后重启后端（`createDatabaseIfNotExist=true` 会重建并跑 `schema.sql`）；
   开发库如需保留数据，先用「数据管理 → 数据导出」，重建后「数据导入」回灌
4. 跑 `tools/db/verify-schema-parity.ps1`：全新库与目标库的 `information_schema` 差集必须为 **0**

## 四、校验脚本（都在 `tools/db/`）

| 脚本 | 用途 |
|---|---|
| `fold-migration-ddl-into-schema.ps1` | （一次性，已完成使命）把 `addColumnIfMissing` 类 DDL 折进 `schema.sql`；幂等 |
| `strip-datainitializer-migrations.ps1` | （一次性，已完成使命）批量剥离 `DataInitializer` 的 `migrate*()`；自带"删除行数 < 400 拒写"防呆 |
| `verify-schema-parity.ps1` | **P1 验收**：全新空库 vs 现库的列/表差集（含类型/可空/默认值），known-drift 白名单 |
| `migration-ddl-inventory.txt` | P0 基线：迁移曾补过哪些列（`INSERT`/`PRESENT`/`TABLE-MISSING` 状态） |
| `restore-pre-clear-rollback.ps1` | 从「清空公司数据」的回滚点 JSON 直连 SQL 回灌（**不要**用 `/import-data`，它会清掉未在备份中的表） |

## 五、已知遗留漂移（不在 `schema.sql` 侧修正）

| 位置 | 现库 | `schema.sql`（准） | 说明 |
|---|---|---|---|
| `finance_bill.status` 默认值 | `UNSETTLED` | `DRAFT` | 现库那条默认值是早年从应收表复制来的；代码始终显式写 `DRAFT`，故以 `schema.sql` 为准；已登记在 `verify-schema-parity.ps1` 的 `$knownDrift` |

## 六、清理动作的兜底（与本次事故直接相关）

`ClearController`（清空本公司/全库）与导入导出属**不可逆路径**，其加固口径见
`docs/代码审核报告_设置模块_20260930.md` §4.5；关键点：

- 清空前**自动落回滚点**（`uploads/clear-backup/company-<id>/pre_clear_company_rollback-<ts>.json`，
  格式同「数据导出」，**可用** `tools/db/restore-pre-clear-rollback.ps1` 或「数据导入」恢复）
- 后端强制 `confirm` 口令；支持 `dryRun` 预演（不删数据）
- 每次清空/导入都写 `sys_operation_log`（演练也留痕）

> 2026-09-30 曾发生一次开发库被真实清空（8664 行 / 100 表），**正是靠上述回滚点完整恢复**
> （逐表行数与时间戳均校验一致）。教训：不可逆路径的"预演 + 回滚点"不是可选项。
