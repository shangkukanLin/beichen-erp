### F7-264（P2 · E2）切回账期不清理 `settle_amount`，账期单残留"本次收款总额"

- **文件:行**：`beichen-erp-server/.../sale/service/impl/SaleOrderServiceImpl.java:455-463`（`update`）；
  对照 `normalizeSettle` 的 218-222（账期分支把两个字段都置 null）与 458-463 的显式清理。
- **现象**：把一张「现金」销售单改成「账期」后，`settle_account_id` 被显式清空、分款行被删除，
  但 `sale_order.settle_amount` **仍保留旧值**（实测残留 `300.0000`）。
- **最小复现**（可复跑脚本：`tools/regression/audit/audit-20261004-multi-account-write-probe.ps1`）：
  ① `POST /api/inventory/sale`（现金 + 两账户 200/100，总额 300）建草稿；
  ② `PUT /api/inventory/sale/{id}`（`settleType=CREDIT`）⇒ ③ 查库：
  `settle_type=CREDIT`、`settle_account_id=NULL`、`split_rows=0`，**但 `settle_amount=300.0000`**。
- **根因**：`update()` 用 `orderMapper.updateById(order)` 落主表，而 **MyBatis-Plus 默认忽略 null 字段**（本文件
  464-468 行注释已写明该机制，并据此为 `settle_account_id` 补了显式 `set(null)`），但**同一处遗漏了
  `settle_amount`** —— 两字段同属"账期无意义"，只清了一个。
- **影响面**：账期单据在**任何读 `settle_amount` 的出口**（详情/列表/导出/后续报表）会显示一个不存在的
  "本次收款总额"，与"账期无收款"口径冲突；**无资金腿影响**（审核路径只在 `settleType=CASH` 时读它，
  见 586 → 294-313），故不涉及金额计算错误。历史数据当前为 0 条（只读探针 H 证实）⇒ **潜伏缺陷**。
- **证据强度**：`E2`（写库实证 + 两个对照：账户被清 ✓、分款行被删 ✓ ⇒ 不对称成立；探针前后 7 张表计数一致 ✓ 零残留）。
- **级别**：P2（口径不一致 / 展示错误；无资金后果）。
- **修复成本**：`S` —— 照 `settle_account_id` 的既有写法追加 `.set(SaleOrder::getSettleAmount, null)`。
- **可自动化断言**：`PUT` 改结算方式为 CREDIT 后，`SELECT settle_amount FROM sale_order WHERE id=?` 必须为 NULL；
  且 `settle_account_id`/分款行数同时为 NULL/0（三者要么一起清、要么都留，禁止半清）。

### F7-265（P2 · 缺口与后果均已 `E2` 实证）无分款行回退分支不校验 `settleAmount` 下界

- **文件:行**：`SaleOrderServiceImpl.java:226-234`（`rows.isEmpty()` 分支：只校验账户存在/未停用，**直接 return**，

### F7-266（P3 · E3）"部分收款差额挂预收"是错误口径文案（三处）

- **文件:行**：`beichen-erp-web/src/components/AccountSplitTable.vue:17`（提示"本次待收 ¥x 将挂预收"）·
  `SaleOrderServiceImpl.java:287-288`（javadoc"差额由收款单审核按未核销余额落预收台账"）·
  `beichen-erp-web/src/views/sale/order/add.vue:105`（同口径注释）。
- **现象**：销售单应收 1000、本次收款 800（部分收款）时，页面提示"本次待收 ¥200 将挂预收"。
- **根因/实况**：自动收款单的核销金额 = **本次收款总额**（`createCashReceipt` 347 行 `it.setThisAmount(received)`），
  而收款单审核的预收条件是 `unsettled = 收款单金额 − Σ核销 > 0`（`FinanceReceiptServiceImpl.java:494-497`）
  ⇒ 部分收款时 `unsettled = 800 − 800 = 0` ⇒ **不生成预收**（预收只在该收款单"未核销完"时产生，
  例如客户已先付过款项导致可核销额小于本次收款）。差额 200 的真实含义是**应收未收**。
- **影响面**：口径误导（用户会以为少收的 200 变成了客户预付款，进而在"预收台账"里找不到而对账困难）。
  不影响金额计算。
- **证据强度**：`E3`（静态：核销额来源 + 预收触发条件两处代码可闭合；只读数据也印证——现有现金单里
  没有"部分收款 + 预收"组合）。
- **修复成本**：`S`（改三处文案为"将留在应收（未收）"，或说明"仅当本次收款未被全部核销时才转预收"）。
- **可自动化断言**：无（文案）；可加一条口径断言：部分收款审核后 `finance_receivable.unpaid_amount = 应收 − 收款`
  且**不存在**对应的预收台账行。

### F7-267（P3 · E3）应收为 0 的现金单无法保存

- **文件:行**：`beichen-erp-web/src/views/sale/order/detail.vue:130`（`Number(head.settleAmount ?? sum) || null`
  ⇒ 0 会被变成 `null`）· 后端 `SaleOrderServiceImpl.java:294`（`normalizeSettleRows` 要求每行金额 `> 0`）。

- **证据强度**：`E3`（静态；两处规则可复核）。
- **修复成本**：`S~M`（需先确认口径：0 元单是否允许走现金结算——若允许，后端要放行 `settleAmount=0` 且
  允许空分款行；若不允许，前端应给明确提示而不是"合计不等于总额"）。
- **可自动化断言**：0 元现金单提交要么成功且 `settle_amount=0`、无分款行，要么被**明确文案**拒绝（不是隐式规则）。

### 2.4 口径项 D-01 定案与修复记录（2026-10-04 · 用户「定 D-01」）

### 3.3 F7-275（P3 · `E3`）导出「产品明细」页脚 SUM 漏算"无明细来源"行 + 注释口径不成立

- **现象**：当一张账单**既有可展开来源、又有无明细来源**（委外/报损/预收台账…）时，第二页页脚的"明细金额合计"会**少算**若干行。
- **根因**（纯算术，`BillStatementExcelBuilder.buildDetailSheet`）：行布局 0 基 = `0 标题 / 1 说明 / 2 表头 / 3.. 数据 / 末行 合计`；数据区行数 = `K`（无明细来源行，各占 1 行）+ `L`（产品行）。但 `lineRows` 只累加产品行，页脚公式区间取 `DETAIL_HEADER_ROW+2 .. DETAIL_HEADER_ROW+1+lineRows`，即 Excel 行 `4 .. 3+L`，而数据区实际到 `3+K+L` ⇒ **尾部 K 行被排除**。K>0 时若尾部含产品行，金额即少算。
- **附带口径问题**：同方法注释称"页脚的 SUM 恰好等于主表「金额」列合计，可互相印证"——**只有**在全部来源都能展开时才成立；有不可展开来源时那些金额根本不进本页（只留一行灰字说明）⇒ 该"互相印证"会让后来者把正常差额当成缺陷。
- **影响面**：导出件（给对方核对用）的合计少算；本库当前账单恰好只有可展开来源（precheck Q1：`SALE_RETURN` 1 + `PURCHASE_RETURN` 1）⇒ **当前不触发**。
- **证据强度**：`E3`（读源码 + 行号算术；建议修后按下方断言补测）。
- **级别/成本**：P3 / S（区间末值改用"数据区最后一行"= `DETAIL_HEADER_ROW+1+lineRows+K`，或在写行时记 `lastDataRow`）。
- **可自动化断言**：造一张含 1 个无明细来源 + 2 个产品行的账单，断言页脚 `SUM(I…)` 区间**覆盖全部数据行**且值 == `Σ signedAmount`。
