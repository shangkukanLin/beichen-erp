# ADR-0008: 引入核销流水表 + 负数应付表达预付/多付

- **状态**: 已采纳
- **日期**: 2026-08-14

## 背景

当前收付款核销存在两个缺陷：

1. **核销关系单向**：付款审核时 `FinancePaymentItem.payableId → FinancePayable` 减未付，但 `FinancePayable` 无反向记录「被哪张付款单核销」。反审核靠「精确回退本单明细」维持平衡，一旦中间有退货反审核等操作介入，余额可能漂移。
2. **超额核销静默截断**：`unpaid = unpaid - amt` 后直接 `.max(BigDecimal.ZERO)`，付款金额超过未付金额时不报错、不记录，多付部分凭空消失。

## 决策

**1. 新建核销流水表 `finance_settlement`**，记录每次核销的完整双向关系：

- `payer_receiver_id`：付款单/收款单 ID
- `payable_receivable_id`：应付/应收台账 ID
- `amount`：本次核销金额
- `direction`：核销方向（收/付）
- `source_type`：来源单据类型
- 反审核时按核销流水精确冲销，不依赖「回退本单明细」的隐式对称

**2. 允许超额，超额部分用「负数应付」表达预付/多付**：

- 不新建预付表；超额金额在 `finance_payable` 插入一条 `amount = -超额额` 的负数应付（负数 = 供应商欠我方 / 预付）
- 实时汇总余额时负数自然抵扣；核销流水表统一记录，无需特殊分支

## 后果

- **正面**：核销关系双向可追溯，反审核精确冲销；超额付款不再丢账，预付余额可抵扣后续应付。
- **负面/代价**：新增一张表 + 一套核销流水写入/冲销逻辑；负数应付使应付台账语义扩展（金额可为负）。
- **不可逆**：核销关系从此以核销流水表为准，旧「按明细回退」逻辑废弃。

## 备选方案

- **超额直接拦截**：`amt > unpaid` 抛异常。被否决——真实业务存在供应商多付场景，需支持。
- **新建预付表 `finance_advance`**：超额部分落独立预收/预付表。被否决——负数应付已能表达，额外建表增加复杂度，且余额汇总要跨两表。
- **核销关系用「明细回退」隐式对称**：现状做法。被否决——单向关系脆弱，需引入显式流水表。
