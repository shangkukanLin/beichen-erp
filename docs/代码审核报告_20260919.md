### 1.1 F7-1（**P0**，已实证）URL 编码绕过接口权限守卫 —— 读写均可越权

**现象**：同一接口，明文路径 403，把前缀里任意一个字符做百分号编码后即 **200**。

| 请求（`perm_test`，无 `finance:payable`） | 结果 |
|---|---|
| `GET /api/finance/payable/page` | `code=403 无权限访问` |
| `GET /api/finance/%70ayable/page` | **`code=200 success`** |
| `GET /api/financ%65/payable/page` | **`code=200 success`** |
| `GET /api/%66inance/payable/page` | **`code=200 success`** |
| 写方法：`POST /api/dev/project`（无 `dev:project`） | `code=403 无权限访问` |
| 写方法：`POST /api/dev/projec%74` | **`code=400 存在必填字段未填写：Field 'name' doesn't have a default value`** ⇒ **已进入持久层** |

（对照：`/api/FINANCE/...` → 404、尾斜杠 → 403、`;a=1` → 403、`/api/../api/...` → 403 ⇒ 只有**百分号编码**这一条路能绕。）

**根因**（`config/SaTokenConfig.java:74-77` + `config/ApiPermGuard.java:248-298`）：
1. 守卫取路径用的是 `request.getRequestURI()` —— 按 Servlet 规范它返回**未解码**的原始 URI；而 Spring MVC 用**解码后**的路径做路由匹配。于是守卫看到 `/api/finance/%70ayable/page`（不命中任何名单），Spring 却把它路由到 `/api/finance/payable/page`。
2. `ApiPermGuard.check()` 在未命中 `EXEMPT / READ_SHARED / RULES / WRITE_RULES` 时**不抛异常、直接返回**（fail-open），且该判断在读写分支之前 ⇒ **方法无关**（写同样绕过）。

**影响**：**任何已登录用户（哪怕只被授了首页）都可以对任意模块读写** —— 越权读数据、越权改库存/资金/单据，属 P0（越权写入）。

**修复建议（供决策，未实施）**：
- 守卫改用**解码且归一化**后的路径：`UrlPathHelper.defaultInstance.getPathWithinApplication(request)` 或 Spring 6 的 `ServletRequestPathUtils.parseAndCache(request).pathWithinApplication().value()`；不要直接用 `getRequestURI()`。
- 把"未命中任何名单"从**放行**改为**拒绝**（默认拒绝 / 至少 `WARN` 后拒绝未知 `/api/**`），避免以后再出现 F7-2/F7-3 这类裸奔前缀。
- 视需要在网关/Tomcat 层对 `%2e`/`%2f` 之类做拒绝（`ALLOW_ENCODED_SLASH=false` 已是默认）。
- **回归断言**：把本节的 6 个 case 写成 `verify-api-perm-bypass.ps1`（明文 403 / 编码 403 才算通过）。

### 1.8 F7-8（P2，静态）`CompanyContext` 在 403/401 路径不清理

**证据链**：
- `SaTokenConfig.addInterceptors()`：拦截器 #1（`SaInterceptor`）里 `StpUtil.checkLogin()` + `CompanyContext.set(cid)` + `apiPermGuard.check(...)`；拦截器 #2 的 `afterCompletion` 里 `CompanyContext.clear()`。
- Spring MVC 只在**某拦截器 preHandle 返回 true** 后才回调它的 `afterCompletion` ⇒ #1 抛 `NotPermissionException`（403）或未登录（401）时，**#2 从未生效 ⇒ ThreadLocal 不清理**。
- `CompanyContext.set(null)` 内部 `if (companyId != null)` ⇒ 即使调用也无法清除；而 super_admin 之类 session 无 `companyId` ⇒ 不会覆盖，**沿用上一请求的脏值**（MyBatis-Plus 租户插件按它过滤 SQL）。
**影响**：数据可见性错误（超管被当某公司过滤）；不构成"越权读他人数据"（下一请求只会被**限制**而非扩大），故 P2。
**建议**：清理改为 `try/finally`（在 SaInterceptor 的 lambda 内 `finally { CompanyContext.clear(); }`，或在 `checkLogin` 前先 `clear()`）。

### 1.9 F7-9（P2，部分已核）`EXEMPT` 含写端点前缀的逐条复核

`EXEMPT` 是"读写都放行"，所以每条都要问：**它下面有没有写端点？靠谁保护？**

| EXEMPT 条目 | 写端点？ | 结论 |
|---|---|---|
| `/api/auth` | 改密、本人信息 | ✅ 仅本人，安全 |

### 3.2 逐条展开

#### 3.2.1 F7-15（**P1**，✅ 已实证）移仓负数量 ⇒ 库存反向搬运

**现象**：`POST /api/inventory/warehouse-move` 建草稿（`fromWarehouseId=76, toWarehouseId=71, items=[{productId=61, qualityType='A', quantity=-2}]`）→ `200`；`PUT /{id}/audit` → `200`。审核后库存**反向变化**。

| 观测 | 期望（单据语义 76 → 71 移 2 件） | 实际 |
|---|---|---|
| `warehouse_stock(wh=76, product=61, quality_type='A').quantity` | 100 → 98 | **100 → 102** |
| `warehouse_stock(wh=71, product=61, quality_type='A').quantity` | 88 → 90 | **88 → 86** |

实测单据 `YC-20260919001`（实证后已还原，见复现脚本）。

**复现**：`beichen-erp/tools/regression/audit/audit-20260919-stock-probe.ps1`（PROBE A；自带备份/回滚/逐表计数自检，`RESULT PASS`）。

**根因**：`inventory/service/impl/WarehouseMoveServiceImpl.java:169-183` —— 审核时按明细 `quantity`（**无 `> 0` 校验**）给移出仓 `q.negate()`、移入仓 `q`；`q < 0` 时两侧符号同时翻转，等价于"反向搬运"。建单（`:109-127`）与编辑（`:129-145`）同样不校验明细数量（可空、可负）。

**影响面**：任何持有移仓页面码的用户，只要提交负数量（前端 `add.vue` 有 `:min="1"`、`detail.vue` 会过滤 `>0`，但**接口无校验**，直连 API 即可）⇒ 单据与账实方向相反、后续盘点/成本/报表全部基于错误方向。数量守恒、不产生负库存（写入层护栏），因此**不会报错，只会静默错账**。反审核同样反向回滚，不会自愈。

**证据强度**：`E1`（已实证，含"未超权限、create+audit 均 200"的对照）。

**级别**：P1（不可逆库存方向错误；触发需构造负数入参，但无需越权）。

**修复成本**：S（在 `create/update` 与 `audit` 三处对明细 `quantity > 0` 校验；或复用 `validItems` 统一过滤）。

**建议**：后端补"数量必须为正"的硬校验（与 `ReclassifyServiceImpl.audit:158-162` 的既有写法一致）；`audit` 再兜一层，避免历史脏草稿。

**可自动化断言**：把 `audit-20260919-stock-probe.ps1` 的 PROBE A 反转为"负数量必须被拒（400）"，纳入 `verify-*` 门禁。

#### 3.2.2 F7-16（**P1**，✅ 已实证）重分类目标品质非法 ⇒ 产生幽灵库存行

**现象**：`POST /api/inventory/reclassify`（`warehouseId=76, items=[{productId=61, fromQuality='A', toQuality='ZZ', quantity=1}]`）→ `200`；`PUT /{id}/audit` → `200`，随后库中出现：

```
warehouse_stock(warehouse_id=76, product_id=61, quality_type='ZZ', quantity=1, company_id=1)   ← 新行
warehouse_stock(warehouse_id=76, product_id=61, quality_type='A' ).quantity  100 → 99
```

**复现**：同上脚本 PROBE B（实测单据 `PC-20260919004`，已还原）。

**根因**：`inventory/service/impl/ReclassifyServiceImpl.java:176-179` 把 `it.getToQuality()` **原样**传给 `strokeService.changeStock(...)`；正数走 `insertStock` 分支直接建行（`WarehouseStockService:77-82`），全程**没有品质白名单校验**（未调用 `ProductQualityType.isValid`）。同类问题在 `fromQuality` 侧表现为**校验/落账口径不一致**：`checkStockBeforeAudit:195-196` 把空串品质当作 `A` 校验，而 `audit:174` 仍把空串传给 `changeStock`（不归一到 `A`）⇒ "校验的是 A、扣的是空串行"。

**影响面**：可写入任意 `quality_type` 的库存行（含空串）。这类行**不落入任何品质口径**（A/B/C/DEFECT/PENDING），使"库存总量"与"各品质之和"不符（账实不符），且会污染 `product-stock` 汇总与后续重分类/整理的可整理量计算。破坏性不可逆（除非人工清理）。前端下拉不会产生非法值 ⇒ **需构造入参**，但无需越权。

**证据强度**：`E1`。

**级别**：P1（不可逆脏库存行 + 口径失真）。

**修复成本**：S（`create/update/audit` 三处统一按 `ProductQualityType` 白名单校验 `fromQuality/toQuality`，并把空串归一为 `A` 或直接拒绝）。

**可自动化断言**：`audit-20260919-stock-probe.ps1` 的 PROBE B 反转为"非法 `toQuality` 必须被拒（400/500 且不落行）"，并断言 `SELECT COUNT(*) FROM warehouse_stock WHERE quality_type NOT IN ('A','B','C','D','DEFECT','PENDING','GOOD') = 0`（可作全局不变量）。

#### 3.2.3 F7-17（P2，静态）其他出入库 `ioType` 未校验枚举，非 `IN` 按出库扣减

`inventory/service/impl/OtherIoServiceImpl.java:95-96` 只校验 `ioType` 非空；`checkStockBeforeOut:217-218` 仅在等于 `OUT` 时校验库存（其它值**跳过校验**）；`applyStock:243-245` 却是"非 `IN` 一律按 `OUT` 扣减 `negate()`"。⇒ 传 `ioType='XYZ'`（或小写 `in`）会**跳过库存校验仍然扣减**，最终由写入层护栏抛"库存不足"通用错误。行为自相矛盾（校验与落账判定条件不一致），且错误信息误导。**影响**：不会超扣（护栏兜底），但语义颠倒 + 报错不可解释。**修复成本 S**（白名单校验 `IoType`，并让三处判定共用同一方法）。**可自动化断言**：非法 `ioType` 必须 400。

#### 3.2.4 F7-18（P2，静态）无租户上下文时库存写入必失败；`company_id` 参与唯一键可致 NULL 重复行

`WarehouseStockMapper.java:16-31` 的 `updateQuantity` 用**硬编码** `AND company_id = #{companyId}`，而 `WarehouseStockService.java:67-68` 在 `CompanyContext` 为空/`<=0` 时把 `companyId` 置为 `null` ⇒ `company_id = NULL` **永不成立**（SQL 三值逻辑），`rows=0` → 落到"存在即抛库存不足"分支（`:71-76`）⇒ **入库也会报"库存不足，无法出库"**。叠加 `warehouse_stock` 唯一键含 `company_id`（`uk_wh_prod_quality_company(warehouse_id,product_id,quality_type,company_id)`，见库内实际索引）——MySQL 唯一索引中 `NULL` 互不相等 ⇒ 若真走到 `insertStock`，可插入**多条 `company_id IS NULL` 的同维度库存行**，把同一批库存拆到多行。**待验证**：`CompanyContext` 在何种账号/调用路径下为空或 `<=0`（超管？定时任务？），据此定级（当前静态判定，未复现）。**修复成本 M**（SQL 改动态条件或统一非空租户过滤；`company_id` 不建议参与唯一键）。

#### 3.2.5 F7-19（P2，静态）加权成本 read-modify-write

`warehouse/service/CostService.java:116-133`：`sumStock()` 读库存量 + `currentCost()` 读主数据 → 计算 → `updateCost()` 写回 `product.cost_price/last_in_price`（`:229-244`）。`@Transactional` 只保证原子提交，**不阻止并发丢失更新**（两笔并发入库相互覆盖加权价）。`sumStock:178-189` 的 `company_id` 过滤为条件式（`companyId` 为空则不过滤）⇒ 冲销时若批次 `company_id` 为空会跨公司汇总（`:153,156` 取批次首行 companyId）。**影响**：成本金额（影响毛利与资金口径）失真；不影响库存数量。**修复成本 M**（行锁 / `SELECT ... ### 7.2 逐条展开

#### 7.2.1 F7-31（**P1**，✅ 已实证）收款核销不校验客户归属 ⇒ 跨客户串账

**现象**：`POST /api/finance/receipt`（`customerId=24`）+ `PUT /{id}/audit` → 均 `200`，随后**客户 16 的应收被核销**：

| 观测 | 期望（收款单属客户 24，只能核销 24 的应收） | 实际 |
|---|---|---|
| `finance_receivable(id=174, customer_id=16)` | 不变 | `paid 0→50`、`unpaid 200→150` |

**复现**：`audit-20260919-finance-probe.ps1` PROBE A（含还原自检，`RESULT PASS`）。

**根因**：`finance/service/impl/FinanceReceiptServiceImpl.java:158-162` 只比对 `subjectType`（同为 `CUSTOMER` 即放行），**未校验 `rec.getCustomerId()` 与收款单 `customerId` 一致**。

**影响面**：任何能建收款单的用户（前端下拉虽按客户过滤，但接口按 `receivableId` 直取）⇒ **把 A 客户的收款挂到 B 客户头上**：B 客户应收被错误结清（欠款消失），A 客户收款金额照记，资金流水照入账 ⇒ 双向错账，且台账状态（SETTLED）**不可逆**（除非人工反审核该收款单）。

**证据强度**：`E1`（含"两个客户归属"的显式对照输出）。

**级别**：P1（资金/往来错账，不可逆）。

**修复成本**：S（核销前补 `customerId`/`supplierId` 一致性校验，报错文案指向具体单据）。

**可自动化断言**：把 PROBE A 的期望反转为"必须被拒（非 200）且应收不变"。

#### 7.2.2 F7-32（**P1**，✅ 已实证）付款核销不校验供应商归属

同上类，`FinancePaymentServiceImpl.java:126-129` 直接 `selectById(payableId)` 后核销，**未校验 `p.supplierId` 与付款单一致**（也未复查 `transferredToReceivable`，尽管下拉已排除）。实测：供应商 34 的付款单把供应商 26 的应付核销成 `paid 10 / unpaid 38`。复现同上 PROBE C。**级别 P1 · 成本 S**。

#### 7.2.3 F7-33（**P1**，✅ 已实证）收付款明细金额无正数校验 ⇒ 负数反向调整台账

**现象**：收款明细 `thisAmount=-50` → 审核 `200`：

| 观测 | 结果 |
|---|---|
| `finance_receipt.amount` | `-50`（主表 = 明细之和，原样接受） |
| `finance_receivable(id=172)` | `paid 0→**-50**`、`unpaid 200→**250**` |

**根因**：`FinanceReceiptServiceImpl.java:169-171` 直接 `unpaid.subtract(amt)`；`create`（126）与 `FinanceReceiptController:105-106` 均无正负校验（付款侧 `FinancePaymentServiceImpl:134` + `FinancePaymentController:120` 同）。**影响**：可用负数"凭空增加应收/应付"（虚增债权债务）或让已收/已付金额变负，进而污染所有余额与账龄口径；资金流水也写出负收入。**级别 P1 · 成本 S**（`create`/`audit` 两处校验 `thisAmount > 0`）。**可自动化断言**：PROBE B 反转为"必须被拒"。

#### 7.2.4 F7-34（P2，✅ 已实证）应付余额两套口径（供应商页 vs 应付汇总/分析）

**证据（DB 实测）**：全局 `SUM(unpaid_amount)`（status ∉ {SETTLED, CANCELLED}）——

| 口径 | 数值 |
|---|---|
| 不排除"已转应收"（`SupplierMapper.sumPayableBalance`，被 `SupplierServiceImpl.fillPayableBalance:114-116` 以 `{SETTLED,CANCELLED}` 调用） | **62,750.00** |
| 排除"已转应收"（`PayableQuery.supplierSummary:84-87`、`SupplierSettlementServiceImpl`、`FinanceAnalysisServiceImpl`） | **63,000.00** |

差额 **250** 正是那笔已被转成应收的 `-250` 应付（`transferred_to_receivable=1` 全库 1 条）。

**根因**：`SupplierMapper.sumPayableBalance:32-44` 的 SQL 只按调用方传入的状态集合排除，**没有 `transferred_to_receivable <> 1` 条件**；而 `PayableQuery.supplierSummary:86` 明确注释"已转应收的冲减项不再参与付款抵扣，应付汇总口径必须同步排除，否则与应收双算"。另 `FinanceAnalysisMapper.payableSummary/payableAging`（:206/:198）同样**未排除**。⇒ 供应商管理页看到的应付余额与应付汇总/结算/分析页**不一致**。**级别 P2 · 成本 S**（统一到"排除已转应收"口径）。**可自动化断言**：断言两处接口对同一供应商返回同值。

#### 7.2.5 F7-35（P2，静态）反审核重算台账状态缺 `PARTIAL`

`FinanceReceiptServiceImpl.java:355-356` 与 `FinancePaymentServiceImpl.java:319-321` 在反审核冲销后把状态推导为 `unpaid+amt<=0 ? SETTLED : UNSETTLED`，**不会回到 `PARTIAL`**；而审核的正常分支会写 `PARTIAL`（`FinanceReceiptServiceImpl:230-231`）。若该台账还被**其它**收付款部分核销（读出的 `unpaid>0`），反审核后状态应仍为 `PARTIAL` 却被写成 `UNSETTLED`。**影响**：状态失真（金额不错，`unpaid` 仍正确；各 `unpaid` 列表口径不受影响）。**成本 S**。

#### 7.2.6 F7-36（P2，静态）付款审核无账户余额校验（与费用不对称）

`FinanceExpenseServiceImpl.java:96-101` 审核前校验"账户实时余额 ≥ 本笔金额"，而 `FinancePaymentServiceImpl.java:211-221` 直接写 `expense = payment.amount` 流水、**无余额校验** ⇒ 付款可使账户余额为负（透支）。差额由前端控制（后端不拦）。**影响**：资金账实不符/口径不一致。**成本 S**（对齐费用单的校验；是否允许透支需产品确认）。

#### 7.2.7 F7-37（P2，静态）收款明细被静默跳过但流水全额入账

`FinanceReceiptServiceImpl.java:154-157`：明细 `receivableId` 为空或台账不存在时 `continue`；而资金流水（`:250-259`）按 `receipt.getAmount()`（**含被跳过项**）全额记 `income` ⇒ "钱进账、应收没减"。若该场景设计上代表"预收款"，则预收**未生成 ADVANCE 台账**（只有超额分支才建），后续无法核销。**待产品确认口径**；**成本 S~M**。

#### 7.2.8 F7-38（P2，静态）`auto-generate` 无参跨公司批量出账

`FinanceBillController.java:50-51` 的 `POST /api/finance/bill/auto-generate` 直接 `autoTask.run(now)`，而 `FinanceBillAutoTask.run:88-120` **遍历所有启用公司**（逐公司设置 `CompanyContext`）生成账单；权限只要求 `finance:bill` 页面码（`ApiPermGuard` 无动作级细分）⇒ 任一持有该页面码的用户可**跨租户**批量写。**成本 S**（限定为平台管理员或当前公司）。

#### 7.2.9 F7-39（P3，静态）一批小问题（合并）

### 11.1 F7-35（P2 · **已 E1 实证**）反审核重算台账状态缺 `PARTIAL`

**现状（两处同构）**：

| 文件:行 | SQL 片段 |
|---|---|
| `FinanceReceiptServiceImpl.unAudit:383-384` | `status = CASE WHEN IFNULL(unpaid_amount,0) + (amt) <= 0 THEN 'SETTLED' ELSE 'UNSETTLED' END` |
| `FinancePaymentServiceImpl.unAudit:346-347` | 同上（应付侧） |

**根因**：审核侧会写三态（`FinanceReceiptServiceImpl:258-259`：`unpaid - amt <= 0 ? SETTLED : PARTIAL`），而**反审核侧只有两态**（`SETTLED/UNSETTLED`）。当该台账**还有其它收付款的部分结清**时（反核销后 `0 < unpaid < amount`），状态应回到 `PARTIAL` 却被写成 `UNSETTLED`。
**实证（§10.3）**：台账 282（`amount=2090 / 已付 500 / 未付 1590 / PARTIAL`）→ 付款 10 并审核 → 反审核 ⇒ 金额正确回退（500/1590）但 **status 变 `UNSETTLED`** ⇒ 该台账在"部分结清"筛选/统计里**消失**（`unpaid` 列表按 `status IN (UNSETTLED,PARTIAL)` 过滤的地方会更严重）。

**拟定改动（2 处，各 +1 行 CASE 分支）**：

```sql
status = CASE WHEN IFNULL(unpaid_amount, 0) + (amt) <= 0                 THEN 'SETTLED'
              WHEN IFNULL(unpaid_amount, 0) + (amt) >= IFNULL(amount, 0) THEN 'UNSETTLED'
              ELSE 'PARTIAL' END
```

- 判定基准用台账自身 `amount`（`unpaid` 恢复到等于 `amount` ⇒ 确实一分未付 ⇒ `UNSETTLED`；介于两者之间 ⇒ `PARTIAL`）。
- `status` 仍写在金额赋值**之前**（MySQL SET 从左到右求值，用更新前的金额判断）——与现有写法一致。
- 影响面：只影响**反审核后的状态字段**，不动金额；对"只有本单付款"的台账行为不变（仍回到 `UNSETTLED`）。

### 11.2 F7-37（P2）收款/付款明细被静默跳过，资金流水却按全额入账

| 选项 | 做法 | 成本 | 评价 |
