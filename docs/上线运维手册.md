### 3.9 越权通道修复（P2-35 · 随 P0 发现）

- **现象**：`CompanyServiceImpl.create` 建公司后，为管理员分配角色时**优先查 `super_admin`**，查不到才回退 `admin`。
- **为何此前没暴露**：写这段代码时 `DataInitializer.initRoles` 只建 6 个角色、**`super_admin` 根本不存在** → 永远走回退（注释里也写明了这一点）。
- **为何成为缺陷**：P2-34 为收口整库运维把 `super_admin` 建了出来 → 该分支**立即生效**：**任何新建公司**的管理员都会拿到**平台级**角色，可直接整库导出/导入/清空（越租户边界）。
- **修复**：改为**显式授予 `admin`**（租户级），并加注释说明 `super_admin` 只能由 `DataInitializer` 授予唯一平台账号 `lin`、且用户管理禁止分配。
- **守护**：`gate.ps1` 新增不变量 —— `super_admin 仅 lin 持有(非 lin 越权)`，任何"非 `lin` 用户持有 `super_admin`"都会让门禁失败。

### 3.2 sa-token 会话在内存 —— 单实例强约束 ⏳（待运维执行，本环境无 Redis 未验证）

- `pom.xml` **无** `sa-token-redis`、**无** `spring-boot-starter-data-redis`；sa-token 配置在 `application.yml:46-52`（`token-name=Authorization`、`timeout=86400`、`is-concurrent=true`、`is-share=true`、`token-style=uuid`）。
- **后果**：① 后端重启 → 全员登录态失效，需重新登录；② **无法多实例部署**（会话不共享）。
- **上线要求（二选一）**：
  - **方案 A（推荐）**：接入 `sa-token-redis` + Redis，改为分布式会话；
  - **方案 B（临时）**：**强制单实例**部署，发版窗口公告"重启后需重新登录"。

**方案 A 接线（待运维执行；本环境无 Redis，未验证）**：

```xml
<!-- beichen-erp-server/pom.xml 的 <dependencies> 内追加两条 -->
<dependency>
    <groupId>cn.dev33</groupId>
    <artifactId>sa-token-redis-jackson</artifactId>
    <version>${sa-token.version}</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

```yaml
# 然后补 Redis 连接（环境变量或 application-prod.yml）
spring:
  data:
    redis:
      host: ${REDIS_HOST:127.0.0.1}
      port: ${REDIS_PORT:6379}
      password: ${REDIS_PASSWORD:}
```

> 引入后 Sa-Token 会自动改用 Redis 作为 `SaTokenDao`（会话跨实例共享、重启不掉线）。
> **验收要点**：① 两个实例交替请求，登录态保持；② 重启任一实例后旧 token 仍可用；③ Redis 不可用时应用启动应报错而非静默降级。

### 3.4 CORS 全放开 ✅（已改为可配置白名单）

**落地**：`SaTokenConfig` 的 `allowedOriginPatterns` 改为读取 `app.cors.allowed-origins`（环境变量 `CORS_ALLOWED_ORIGINS`，逗号分隔），默认仍为 `*`（保持本地开发联调不变）；生产 profile **无默认值**，必须显式填写，如 `https://erp.example.com`。

`config/SaTokenConfig.java`：`allowedOriginPatterns("*")` + `allowCredentials(true)` → 任意站点可带凭证调用。**上线要求**：收敛为生产域名白名单。

### 3.5 定时任务无单实例保护 ✅（已加开关 + MySQL 命名锁）

**落地**：`FinanceBillAutoTask`
1. 类上加 `@ConditionalOnProperty(name = "app.scheduling.enabled", havingValue = "true", matchIfMissing = true)` —— `SCHEDULING_ENABLED=false` 时整个 Bean 不装配（生产多实例可只让一个实例开）；
2. 新增 `runScheduled()`：定时入口先用 **MySQL `GET_LOCK('beichen:finance-bill-auto', 0)`** 抢占本轮执行权，抢不到即 `log.info(... 本轮跳过)`；执行完 `RELEASE_LOCK`。
   - 锁绑在取出的连接上，**进程崩溃/连接断开由 MySQL 自动释放**，不会"锁泄漏导致任务永不执行"；
   - 无需引入 Redis/ShedLock、无需新建表；
   - 手动触发接口仍走 `run()`（**不受锁限制**，因为那是人主动点的）。

| 任务 | 位置 | 调度 | 作用 |
|---|---|---|---|
| `FinanceBillAutoTask.autoGenerateDaily` | `finance/task/FinanceBillAutoTask.java` | `cron = "0 0 2 * * ?"`（每日 02:00） | 扫描到期未结清应收/应付，自动生成**草稿**账单 |

- **无任何分布式锁 / 配置开关**（无 `@SchedulerLock`、无 Redis 锁、无 `@ConditionalOnProperty`）。
- **上线要求**：多实例部署必须加分布式锁（`ShedLock`/Redis 锁）或**指定仅一个实例开启调度**；单实例部署可接受。
- 注：生成的是**草稿**账单（不直接生效），重复生成的后果是"重复草稿"而非重复入账，但仍需清理。

### 3.6 前端生产托管 ✅（样例已提供）

- 仓库**无 nginx 配置样例**（全仓搜 `*.conf` = 0）。生产需自建：静态托管 `dist/` + 反代 `/api → 后端:8080`，并**开启 gzip**、配置 `try_files $uri $uri/ /index.html`（前端为 history 路由）。
- `vite.config.ts` 未设 `base`（默认 `/`）、未设 `outDir`（默认 `dist`）。

### 3.7 日志 ✅（已落盘 + 轮转）

**落地**：`logging.file.name=${LOG_FILE:./logs/beichen-erp.log}` + `logging.logback.rollingpolicy`（单文件 50MB、保留 30 个历史、总量上限 2GB）。默认路径相对**启动工作目录**（用 `mvn spring-boot:run` 时为 `beichen-erp-server/logs/`；实测 `FileController` 打印上传目录为 `...\beichen-erp-server\uploads`）。生产用绝对路径（`LOG_FILE=/var/log/beichen/beichen-erp.log`）。

> **为什么这条最关键**：P2-34 的整库运维**审计日志**（`[审计] 整库导出/导入/清空`）与 A3 的**负库存告警**都是 WARN 级；此前只进控制台、一重启即丢失 —— 落盘后 §6.6 的审计检索与 §8.3 的告警巡检验才真正可用。

**原始差距（已解决）**：

- **仅控制台输出**（无 `logging.file`、无 `logback*.xml`）。生产必须落文件 + 轮转，否则**审计与告警日志不可追溯**（见 §6.6、§8.3）。
- 当前本地脚本通过重定向落盘：`%TEMP%\beichen-server.log`、`backend_restart.log`、`be_compile.log`、`web_dev.log`。

## 5. 账号与权限模型

### 5.1 三层角色

| 层次 | 角色 | 持有人 | 能力边界 |
|---|---|---|---|
| **平台级** | `super_admin` | **仅 `lin`**（启动自愈授予） | 跨租户**整库**运维：导出/导入/全库清空 |
| **租户级** | `admin` | `lin` + 各公司 `adminN` | 本公司全部业务 + **本公司数据清空** |
| **业务级** | `dev_engineer` / `sales` / `warehouse` / `merchandiser` / `finance` | 由管理员分配 | 按菜单/接口授权 |

**关键约定（务必遵守）**：

1. **用户管理界面禁止分配 `super_admin`**（`UserServiceImpl.saveUserRoles` 会跳过该角色）→ 公司管理员**无法自提权**为平台超管。
2. `super_admin` 是**能力角色**（后端高危端点校验 + 前端 `isSuperAdmin` 门控）；「数据管理」菜单可见性由 `admin` 角色提供（`lin` 两者都有）。
3. **若发现 `lin` 调用平台级接口返回 403** → 说明其 `super_admin` 关联丢失，**重启后端即自愈**（`ensureLinRole`）；也可手工：`INSERT INTO sys_user_role(user_id, role_id) SELECT 1, id FROM sys_role WHERE role_code='super_admin';`
4. 平台级共享资源（角色/菜单）以 `company_id=0` 为哨兵；业务数据一律带真实 `company_id` 并由 `CompanyContext` 过滤。

### 5.2 会话

- 登录：`POST /api/auth/login` → 返回 token；前端存 localStorage，放入请求头 **`Authorization`**。
- 有效期 **86400 秒（24h）**；`is-concurrent=true`（多端可同时在线）、`is-share=true`（同端共享同一 token）。
- **重启后端 = 全员掉线**（内存会话，见 §3.2）。

## 6. 整库运维操作（核心章节）

> 本章对应 P2-34 口径（2026-09-12 定稿）。**判断标准只有一条：这次操作是否跨租户。** 跨租户＝平台级＝仅超管；不跨租户＝公司级＝管理员可用。

### 6.1 权限口径总表

| 端点 | 语义 | 是否跨租户 | 可调用角色 | 前端入口 | 审计日志 |
|---|---|---|---|---|---|
| `GET /api/system/export-data` | **整库导出**（所有公司、所有表，含 `sys_user` 密码哈希） | ✅ 是 | **仅 `super_admin`** | 数据管理 → 数据导出 | `[审计] 整库导出` |
| `POST /api/system/import-data` | **整库替换**（先 `DELETE` 全库再重建） | ✅ 是 | **仅 `super_admin`** | 数据管理 → 数据导入 | `[审计] 整库导入开始/完成` |
| `POST /api/system/clear-data` | **整库清空**（遍历所有表 `DELETE`） | ✅ 是 | **仅 `super_admin`** | **无界面入口**（仅 API） | `[审计] 全库清空开始/完成` |
| `POST /api/system/clear-company-data` | **本公司**业务数据清空 | ❌ 否 | `admin` | 数据管理 → 清空数据 | 无（业务操作，建议自查日志） |
| ~~`GET /api/system/check-menu`~~ | 遗留调试端点（读 `sys_menu`/`sys_role_menu`） | — | — | — | **已删除**（P2-34） |

**权限实现方式（供排障）**：
- `SystemController`：**类级** `@SaCheckRole(SUPER_ADMIN_ROLE_CODE)`；
- `ClearController`：**类级** `{super_admin, admin}`（为保住公司级清空）+ 在 `clear()` 上加**方法级** `@SaCheckRole(SUPER_ADMIN)` 再收紧（Sa-Token 类级与方法级**都校验**）。
- 前端 `views/system/data-manage/index.vue`：导出/导入两个页签 `v-if="isSuperAdmin"`（非超管只剩「清空数据」）。

### 6.2 导出（备份）

**前端**：登录 `lin` → 系统管理 → 数据管理 → 「数据导出」→ 导出全部数据（浏览器下载 `backup_YYYY-MM-DD.json`）。

**命令行**：

```bash
TOKEN=$(curl -s -X POST http://<host>:8080/api/auth/login \
  -H "Content-Type: application/json" -d "{\"username\":\"lin\",\"password\":\"<口令>\"}" \
  | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

curl -s -H "Authorization: $TOKEN" http://<host>:8080/api/system/export-data -o backup_$(date +%F).json
```

**产物结构**：`{ exportInfo: { time, tableCount, recordCount }, tables: { <表名>: [行…] } }`。

**校验**：`exportInfo.recordCount` 与各表行数之和一致；文件可被 `python -m json.tool` 解析。

### 6.3 导入（恢复 / 迁移）

> ⚠️ **语义 = 用备份"整体替换"当前库**：先对所有 BASE TABLE 执行 `DELETE`（含备份中没有的表），再按备份逐表插入，最后 `SET FOREIGN_KEY_CHECKS = 1`；**在一个事务内**，失败即 `rollback`。**绝不与现有数据合并**。

**前置条件（缺一不可）**：
1. 已获得**停机窗口**（导入期间库不可用）；
2. 已对**当前库另做一份导出/`mysqldump`**（否则导入一旦成功，新数据无路可退）；
3. 备份文件经 `exportInfo` 确认"版本与目标库表结构兼容"（旧备份可能缺表 → 日志会显示"跳过: 当前库无此表"）；
4. 备份文件大小 < **200MB**（`multipart` 上限，见 §3.1）。

**操作**：数据管理 → 「数据导入」→ 拖入 JSON → 「下一步」核对 `备份时间/数据表/总记录数` → 输入 **`确认导入`** → 确认。

**结果核对**：返回 `{ totalTables, totalRecords, exportTime, details }`；`details` 中若某表出现 `"失败: …"` 则整体已回滚。

### 6.4 公司级清空（`clear-company-data`）

- **作用**：清空**当前登录公司**的业务数据（按 `CompanyContext` 逐表 `DELETE ... WHERE company_id = ?`），保留系统表（公司/用户/角色/菜单）与行业基础资料 `screen_model`。
- **权限**：`admin` 可用（租户内自服务）。
- **超管注意**：超管未选择公司时（`companyId` 为空/0）会被拒：`超管模式下请先选择公司`。
- **不可恢复**，执行前务必导出。

### 6.5 全库清空（`clear-data`）—— 灾难级，仅超管

- **作用**：遍历全库 BASE TABLE 执行 `DELETE`（排除 `screen_model`），**所有公司数据一并清空**。
- **无前端入口**，仅为 API；**仅 `super_admin` 可调**。
- 仅用于"完全重置演示/测试环境初始化"。**生产环境建议直接不暴露此路由**（或二次改造为需要密码二次确认）。

### 6.6 审计留痕与检索

所有整库级操作均写 **WARN 级审计日志**（含操作人与规模）：

```
[审计] 整库导出：operator={}, companyId={}, tables={}, records={}
[审计] 整库导入开始：operator={}, companyId={}, file={}, size={}
[审计] 整库导入完成：operator={}, tables={}, records={}
[审计] 全库清空开始：operator={}, companyId={}
[审计] 全库清空完成：operator={}, tables={}
```

**检索（日志落文件后）**：

```bash
grep "\[审计\]" /var/log/beichen/server.log              # 全部整库运维动作
grep "整库导入开始" /var/log/beichen/server.log          # 谁在何时用哪份备份重建了库
```

> ⚠️ 当前日志仅控制台（§3.7）→ **必须先解决日志落盘，审计才真正可用**。

### 6.7 红线（禁止事项）

| # | 禁止 | 原因 |
|---|---|---|

## 7. 八项架构债的运维须知（A3 / C2 / C3 / C5 / D5 / E1 / E2 / E4）

> 这 8 项**不是待修缺陷，而是已定稿的口径**（2026-09-12 定稿，门禁套件 `A3/C2/C3/C5/D5/E1/E2/E4` 30 条断言守护）。运维/报表/后续开发**不要"顺手改回去"**。

### 7.1 逐项说明

| 编号 | 现象（容易被误判成 bug） | 口径（为何刻意如此） | 运维如何正确判读 |
|---|---|---|---|
| **A3** | 委外仓出库后库存变**负数** | 委外仓"强制出库"业务上允许先出后补 → **不拦截**；已在唯一物料写入口加**负库存告警** | `grep "委外仓强制出库导致负库存"` 定位（日志含 warehouseId/materialId/before/after/changeType/relatedCode）；负数即"待补料"，需跟单补单而非改库 |
| **C2** | 移仓**审核与反审核**写了同样的 `MOVE_IN`/`MOVE_OUT` | 这两个 code 表**方向**（某仓进/出），不表**动作**；动作由 `related_bill_type` 区分（审核=`WAREHOUSE_MOVE`，反审核=`WAREHOUSE_MOVE_UN_AUDIT`） | 判读流水时**必须同时看 `change_type` + `related_bill_type`**；历史流水无法回填新 code，故不新增 `MOVE_UN_AUDIT_*` |
| **C3** | 盘点**审核与反审核**共用 `STOCK_TAKE_IN`/`STOCK_TAKE_OUT` | 同上：表"盘盈/盘亏方向"；反审核 = 把 delta **取反**（原盘盈的反审核记为 `STOCK_TAKE_OUT` 的负数） | 用 `related_bill_id`（盘点单）+ 盘点单自身差异正负还原动作 |
| **C5** | 发料反审核时两个仓写不同 code | **已统一**：来源仓与目标仓一律 `OUTSOURCE_CANCEL_DELIVERY`；`CANCEL_DELIVERY` 已 `@Deprecated`（库中无该 code 流水） | 报表只需认 `OUTSOURCE_CANCEL_DELIVERY`；若见到 `CANCEL_DELIVERY` 属**上线前历史数据**（本环境为 0 行） |
| **D5** | 台账单号规则 | **不再拼接 `付款单号-ADVANCE` 当台账号**：**预付**走 `YF-` 流水号（`PayableHelper.newBillNo()`）；**预收**按应收台账命名规则取 `收款单号-ADVANCE`（`ReceivableHelper.advanceBillNo`） | 与来源的关联一律看 `source_bill_type` / `source_bill_no` / `source_id`（反审核按 `source_id` 精确冲回）；不变量断言"`-ADVANCE` 拼接台账号 = 0 行" |
| **E1** | 不同模块的反审核路径拼写不一 | **canonical 统一**：反审核 `PUT /{id}/un-audit`、审核族 `PUT`；旧路径（`/unaudit`、`/unAudit`、`/unapprove`）与旧方法（`POST`）**保留为别名** | 排障抓包见到旧路径**不是 bug**；新代码/脚本请用 canonical |
| **E2** | 品质重分类的 `/cancel` 到底干嘛 | **语义已拆分**：重分类 `PUT /{id}/un-audit` = 反审核（逆向库存 → `CANCELLED`）；`PUT /{id}/cancel` = **仅草稿作废**。退货整理的 `cancel` 本就是"反审核"语义（`AUDITED→DRAFT`），已补 canonical `/un-audit`，`/cancel` 为别名 | 重分类"已审核想撤"→ 用**反审核**；"草稿不要了"→ 用**作废**/"删除" |
| **E4** | 发票没有审核按钮；加工退货草稿不能改 | ①**发票 = 登记即生效**（税务口径：`create` 即生效，`cancel` 仅标记作废）→ **不存在审核态，无需审核端点**；②加工退货**已补** `PUT /outsource/return-order/{id}`（**仅 DRAFT**，明细整体替换）并开放"编辑"入口 | 发票"已登记/已作废"两态即为完整生命周期；加工退货要改动必须先确保是**草稿**（已审核拒绝编辑） |

### 7.2 流水 code 速查（报表/对账必读）

| 场景 | change_type | 关键区分字段 |
|---|---|---|
| 移仓（审核） | `MOVE_IN` / `MOVE_OUT` | `related_bill_type = WAREHOUSE_MOVE` |
| 移仓（反审核） | `MOVE_IN` / `MOVE_OUT` | `related_bill_type = WAREHOUSE_MOVE_UN_AUDIT` |

## 9. 故障处置手册

| 现象 | 可能原因 | 定位 | 处置 |
|---|---|---|---|
| 重启后**全员被迫重新登录** | sa-token 内存会话（§3.2） | 现象即可判定 | 计划内接受；长期方案接 Redis |
| 平台级接口（导出/导入/清空）返回 **403** | `lin` 的 `super_admin` 关联丢失，或用了公司管理员账号 | `SELECT r.role_code FROM sys_user u JOIN sys_user_role ur ON ur.user_id=u.id JOIN sys_role r ON r.id=ur.role_id WHERE u.username='lin';` | **重启后端自愈**；或手工插 `sys_user_role` |
| 反向：公司管理员竟能导出/清空 | 收口被回退（注解被删） | 检查 `SystemController` 类级 `@SaCheckRole`、`ClearController.clear()` 方法级注解 | 恢复注解并跑 `gate.ps1` |
| **账单草案重复生成** | 多实例同时跑 02:00 定时任务（§3.5） | 日志两次 `FinanceBillAutoTask` 输出 | 加分布式锁 / 单实例；清理重复草案 |
| 库存出现负数（**委外仓**） | 允许先出后补（A3，非故障） | `grep 委外仓强制出库导致负库存` | 跟单补料；若**自有仓**出现负数 → 真故障，查流水与单据 |
| 库存出现负数（**自有仓**） | 绕过校验写库/脚本直改 | 流水最后一条与 `before/after` 比对 | 走单证回补，勿再直改库 |
| 导入报 `Maximum upload size exceeded` | 备份 > 200MB（§3.1） | 前端上传即失败 | 调大 `max-file-size` 或分批/清理数据 |
| 导入后"少了数据" | 备份本身不全 / 旧版本缺表 | 返回 `details` 中 `跳过: 当前库无此表` | 换正确备份；**恢复前先导出当前库** |
| 上传文件报错 `无法创建上传目录` | 启动工作目录不同 / 无写权限（`./uploads` 相对路径） | `log.info("文件上传目录: {}")` 看实际路径 | 改为绝对路径并授权 |
| 中文乱码 / PS 脚本解析报错 | 脚本缺 UTF-8 BOM（PS 5.1） | 乱码或语法错 | `fix-bom.ps1` 补 BOM |
| 后端起不来，8080 被占 | 端口冲突 | `netstat -ano \| findstr :8080` | `kill8080.ps1` 或换端口 |
| 前端刷新 404 | nginx 缺 history 回退（§3.6） | 直接访问子路由 | 加 `try_files $uri $uri/ /index.html` |
| 跨域被浏览器拦 | 生产域名不在白名单（§3.4） | Console CORS 报错 | 收敛/补充 `allowedOriginPatterns` |

|---|---|---|---|
| 数据库 | 全库结构与数据 | `mysqldump -uroot -p beichen_erp > dump_YYYYMMDD.sql` | 每日 + 发版前 |
| 业务快照 | 全库 JSON（跨版本迁移用） | 平台超管 → 数据管理 → 导出（或 §6.2 curl） | 发版前 + 月度 |
| 文件 | 上传附件目录 | 复制 `uploads/` | 每日 |

**恢复顺序**：停服 → 恢复 MySQL（`mysql < dump.sql` 或经「数据导入」整体替换）→ 恢复 `uploads/` → 启动 → 跑 `gate.ps1` 确认 9 项不变量全为 0。

**演练要求**：**每季度**在生产同构环境做一次"导出 → 清空测试库 → 导入 → 校验"闭环，确认备份**真的可用**。
