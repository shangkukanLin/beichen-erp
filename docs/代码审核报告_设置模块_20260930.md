### 1.3 条目展开

#### F8-01（P2，E2）`/api/company/list` 匿名可读全部公司（与注释矛盾）
- **现象**：`CompanyController:85-89` 注释「获取所有公司（**需登录**）」，但 `SaTokenConfig:77` 把 `/api/company/list` 列入 `excludePathPatterns`，而该拦截器（`:42-69`）**同时**承担 `StpUtil.checkLogin()` 与 `apiPermGuard.check(...)` ⇒ 排除即"无登录 + 无权限"。
- **最小复现（已跑）**：`GET /api/company/list`（`Authorization: invalid-token`）⇒ `{"code":200,"msg":"success"}` 且返回 `[{id:1,companyName:"北辰科技",…},{id:2,companyName:"B8租户测试B",…}]`；`Company` 实体含 `taxNo`（税号）/`phone`/`address`/`contactPerson`/`email`（`Company.java:12-17`）。
- **影响面**：**未认证**即可枚举全部租户的公司档案（含税号与联系方式）⇒ 跨租户信息泄漏 + 为 `admin/verify` 的口令暴力提供"用户名/公司口径"上下文。
- **级别/成本**：**P2** / **S**（从排除清单移除；若登录页需要公司名，改用已在排除清单内的 `/api/auth/company-name`，或让该接口仅返回 `id + companyName` 并只对已登录用户放开）。
- **可自动化断言**：无 token `GET /api/company/list` ⇒ **401**；已登录低权 ⇒ 仅返回所属公司或 403。

#### F8-02（P3，E2）`SaTokenConfig` 排除清单绕过"默认拒绝 + 启动自检"
- **现象**：白名单在两处（`ApiPermGuard.EXEMPT` 与 `SaTokenConfig.excludePathPatterns`），口径不一致（如 `/api/company` 整个前缀在 EXEMPT，而 `/api/company/list`、`/api/company/admin/verify` 又在排除清单里重复出现）；`ApiPermGuardSelfCheck` 只遍历 Spring MVC 端点校验"是否登记在 guard 四表"，**不读 `SaTokenConfig`** ⇒ 排除清单是**自检盲区**。
- **影响面**：新增/误加一条排除即**静默**放开登录或权限（F8-01 就是实例）；与财务轮 `F7-225`/`F7-255` 同族（白名单面缺方法/清单级断言）。
- **级别/成本**：P3 / S（建议：① 自检增加"排除清单 ⊆ 显式白名单，且每条必须有理由注释"断言 ② 或统一为单一白名单来源）。
- **可自动化断言**：`SaTokenConfig` 排除清单每条都能在 `ApiPermGuard` 的显式白名单中找到对应项，否则启动 ERROR。

#### F8-03（P3，E2/E3）`sys_param` / `sys_operation_log` 无公司条件（多租户缺口）
- **现象**：`SysSettingsController:41-45` `getParams()` 仅 `orderByAsc(id)`；`:62-77` `getLogs()` 无 `CompanyContext` 条件；`:47-59` `saveParams()` 对 `id != null` 的行直接 `updateById`（跨公司行可被改，仅受 `system:settings` 码门控）。`CompanyTenantHandler` 忽略 `sys_*` ⇒ **无插件兜底**。
- **影响面**：多公司投产后，"系统参数"与"操作日志"两页会显示**他公司**数据；`PUT /params` 可改他公司行。当前两表 **0 行** ⇒ 未暴露（**潜在**）。
- **级别/成本**：P3 / S（给两处查询补 `company_id` 条件、写入前校验行归属；或正式拍板"参数/日志为**全局**口径"并在注释与 UI 写明）。
- **可自动化断言**：造第二家公司参数/日志夹具 ⇒ 公司 1 账号读不到公司 2 的行。

#### F8-04（P3，E3）`admin/verify` 无限试 + 超管角色兜底 `1L`
- 见 §1.1；成本 S（加失败计数/锁定；兜底改为"角色行缺失即拒绝"）。

### 2.3 条目展开（关键点）

#### F8-06（P1，E2）`resetPassword` 缺超管护栏 ⇒ 同公司 admin 接管超管
- **最小复现（已跑，自清）**：`lin`（超管，company 1）建临时同公司 `admin`（`roleIds=[1]`）→ 该 admin 登录取 token → `PUT /system/user/reset-password {"id":1,"password":"probe_pw_9x7"}` ⇒ **`code=200 msg=success`** → `POST /auth/login {lin, probe_pw_9x7, companyId:1}` ⇒ **成功** ✓✓。
- **对照负例**：同 admin 重置 **company 2** 的 `admin2` ⇒ **`403 无权限操作该用户`** ✓ ⇒ 护栏存在，但**不覆盖"目标为超管"这一维**。
- **影响面**：同公司任何持 `admin` 者 ⇒ 可登录超管 ⇒ 得 `companyId=0` 会话（`switch` 任意公司、建/删公司、`/api/system/**` 全权）⇒ **跨租户完全接管**。
- **级别/成本**：**P1** / **S**。口径建议：目标为 `SUPER_ADMIN_USERNAME` 时**一律拒绝**，除非操作者本人即超管。
- **可自动化断言**：同公司 admin reset 超管 ⇒ 非 200；超管本人 reset 自己 ⇒ 200。

#### F8-08（P1，E2）`updateUser` 静默剥离超管角色（永久降权）
- **现象**：`saveUserRoles` 的"跳过 super_admin"本意是**防止经用户管理页分配超管**（合理），但 `updateUser` 是 "**先全删、再重建**"(`:210-212`) ⇒ 该 `continue` 变成"**删除后不再恢复**"。

- **级别/成本**：**P1** / **S**。修法：① `updateUser` 对超管目标拒绝（同 F8-06）② `saveUserRoles` 改为"**保留**既有 super_admin 行"而非"跳过插入"（仅在**新建**路径禁止分配）③ 建议两者同做。
- **可自动化断言**：对超管执行一次 `PUT /system/user` 后，其角色集合**保持不变**。

#### F8-07（P2，E2）`updateUser` 可锁死超管（与 `toggleStatus` 护栏不一致）

### 5.3 条目展开（关键点）

#### F8-21（P2，E2）启动同步覆盖菜单编辑（"菜单管理"页形同虚设）
- **最小复现（已跑，零净变更）**：`UPDATE sys_menu SET menu_name='F8-21-REVERT-TEST', sort_order=99, visible=0, status=0 WHERE id=908` ⇒ `restart-backend.ps1`（28s 就绪）⇒ `SELECT` 得 `清空本公司数据 | 8 | 1 | 1` ⇒ `SELECT COUNT(*) ... LIKE '%F8-21-REVERT-TEST%'` = **0**（无残留 ✓）。
- **根因**：菜单种子用 `ON DUPLICATE KEY UPDATE` 把**展示字段**（`parent_id/menu_name/menu_type/route_path/route_name/icon/sort_order`）连同 `visible=1/status=1` 一起写死 —— 目的是"代码改了菜单，升级后自动生效"，副作用是**用户的编辑永远存不住**。
- **影响面**：菜单管理页的"编辑 / 隐藏 / 停用"在重启后全部回滚；用户按自己业务改名/调序/收起不用的菜单会**反复失效**且无任何提示（也解释了历史 15 段"补授块 + 下线菜单"为何都在种子侧维护）。
- **级别/成本**：**P2** / S~M。三种修法（需业务拍板）：① 菜单管理页**只允许新增**，编辑/停用置灰并注明"由系统种子维护" ② 给 `sys_menu` 加 `customized` 标记，被用户改过的行**跳过** upsert 的展示字段 ③ 把 upsert 收窄到**结构字段**（`route_path/route_name/menu_type/icon`），把 `menu_name/sort_order/visible/status` 交给用户（风险：改名不再自动下发）。
- **可自动化断言**：改 `sys_menu` 的 `menu_name/sort_order/visible` ⇒ 重启 ⇒ 值**保持用户设定**（当前断言为"被打回"，即守护反例）。

#### F8-22（P3，E3）新增菜单码不自动补授存量角色（17 段救火块）
- **证据**：`syncMenus:543-550` 只为 `role_code='admin'` 授权；`assignRoleMenus:1547-1561` 的写入条件是 `existingMenuIds.isEmpty()`（`:1557`）⇒ **非空就整体跳过**；存量补齐全靠 `:1106-1290` 的 **17 段**手写 `INSERT IGNORE`。
- **影响面**：新增页面菜单若忘记补授，**已存在的业务角色看不到新菜单**（升级后"功能上线了但没人能进"）；反之，救火块越堆越多、易漏易重。
- **级别/成本**：P3 / S（把"角色 → 菜单码"改成**声明式映射表**，启动时按差集幂等补齐；注意与 F8-21 的"尊重用户改动"口径要一致 ⇒ 建议同时引入 `customized` 语义）。
- **可自动化断言**：菜单表新增一行后重启 ⇒ 每个应授角色都已绑定（或显式登记进"不授"白名单）。

#### F8-23（P3，E2）默认业务种子只服务第 1 家公司 + 孤儿租户数据
- **量化**：`dev_phase_template` 27 行**全 company 1**、`outsource_contract_template` 2 行**全 company 1**；而 `sys_company` 有 2 家 ⇒ **公司 2 无阶段模板/合同模板**。`material_type` 有 company 1/2/3 各 9 行而 `sys_company` 无 id=3 ⇒ **孤儿数据**。

- **级别/成本**：P3 / S~M（① `CompanyServiceImpl.create` 时为公司补默认数据 ② 启动按公司遍历补齐缺失默认（幂等）③ 孤儿行并入清理脚本）。
