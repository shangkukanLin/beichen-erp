## 2. 批 1：采购换货单（`purchase/service/impl/PurchaseExchangeServiceImpl.java` 等）

### 2.1 F1-1（P1）审核时「可换量」把自己算进去 —— **已实证（采购 + 销售两侧）**

**根因**（代码路径）：
```
audit(id):
  DocStatusGuard.claim(... DRAFT → AUDITED)      // 同一事务内先把自己置为"已审核"
  ...
  checkCanExchange(items)                        // 再统计"已换量"
      → alreadyExchangedBatch(): selectList(status = 'AUDITED')   // ← 未排除自身，把自己也统计进来
  判定: thisQty > (已购 − 已退 − 已换[含自身])
```
自查可得等价判定：`退回量 > (可换余量) / 2` 即被拒（首张换货单时 `可换余量 = 已购 − 已退`）。

**实证 A（采购换货）**：`purchase_order_item 267`（产品 60，已购 100，已退 10，已换 14 ⇒ 真实余量 **76**）

| 步骤 | 请求 | 结果 |
|---|---|---|
| 1 | 创建（退回 **50**） | `{"code":200,"code":"CH-20260918011"}` **成功**（创建时不把自己计入 ⇒ 50 ≤ 76 通过） |
| 2 | 审核 | `{"code":500,"msg":"产品[测试产品A11]退回数量超过可换数量（**已购100，已退10，已换64，可换26**）"}` ← `已换64 = 既有14 + **本单自己50**` |
| 判读 | — | 正确应按「库存不足（需 50 / 可用 8）」报错；当前是**数量判据误杀** |

**实证 B（销售换货，同源缺陷）**：`sale_order_item 253`（已售 5，已退 0，已换 0 ⇒ 真实余量 5）

| 步骤 | 请求 | 结果 |
|---|---|---|
| 1 | 创建（退回 3） | `HH-20260918003` **成功** |
| 2 | 审核 | `{"code":500,"msg":"产品[MFTESTE2E2]换货数量超过可换数量（**已售5，已退0，已换3，可换2**）"}` ← `已换3` = 本单自己 |

**影响放大（前端默认值）**：`purchase/exchange/add.vue:199-217` 把退回数量默认填成**可换量全部**（`quantity: qty, maxQuantity: qty`），而审核判据为 `qty > 余量 − qty = 0` ⇒ **凡按默认值直接保存的换货单，审核必然失败**（用户只能手工把数量改到不足余量一半才能审过）。销售侧 `sale/exchange` 若同样默认全额，则同样成立。

**建议修法**（二选一，推荐 ①）：
1. `checkCanExchange/checkCanExchangeMap` 增加 `excludeExchangeId` 参数，聚合时 `ne(id, 当前单)`（销售侧同改）；
2. 或把数量复检挪到 `claim` **之前**（会牺牲 CAS 保护的时间窗，不推荐）。

### 3.1 F2-1（P2）不良退货「未选成品出库仓」会漏扣成品库存

`audit:448-463`：
```java
if (invWhId != null) { ...逐行 changeStock(成品 −qty)... }
else if (repair) { throw new BusinessException("请选择送修出库仓（我方成品仓）"); }
```
⇒ 非维修（不良退货）且 `warehouseId == null` 时**既不报错也不扣成品**，但第 1 步「退货物料入工厂委外仓」（`:437-443`）与第 3 步「负向应付」（`:466-470`）照常执行 ⇒ **料账/应付动了、成品没动**，账实不符。

### 3.2 F2-2（P2）成品退货缺服务端「不超交货」护栏

## 10. F3-3 专项：接口级权限（2026-09-18 立项并实施 v1）

### 10.1 缺口与目标

**缺口（立项依据）**：`StpInterfaceImpl.getPermissionList` 恒返回空、全后端无 `@SaCheckPermission`；
67 个 Controller / ~**469 个端点**中，仅 4 个类级 + 5 个方法级有 `@SaCheckRole`（约 94% 端点**登录即可访问**）。
用户级页面权限此前只做"页面准入"（前端不显示菜单），**被收权者直调接口仍可成功**。

**目标**：把"页面可见性"变成"接口可达性"的同一件事 —— 用户被收掉某页面后，**直调该模块接口即 403**。

### 10.2 口径（关键决策）

| 决策点 | 采用口径 | 理由 |
|---|---|---|
| 权限粒度 | **页面级**（`模块:资源`，如 `purchase:exchange`） | 与侧栏菜单同源 ⇒ 不会出现"页面可见但接口被拒"的自相矛盾；按钮级权限需先有"按钮菜单 + 授权 UI"，属下一阶段 |
| 权限来源 | 用户**可见菜单**的 `sys_menu.perms` 集合（`MenuService.collectPerms`） | 复用既有 `getMenuTreeByRoleIds`（已含 CUSTOM/ROLE 两种模式 + 祖先补齐 + F3-1 的 visible 过滤）⇒ 与前端菜单**零口径差** |
| 下发方式 | 登录时写入 session（同 `roles`） | 零查询开销；与既有 `@SaCheckRole` 行为一致（授权变更**需重新登录**生效） |
| 超管 | `super_admin` 角色**不挂菜单**（DB 实测 0 条）⇒ 兜底给**全量码**（`MenuService.listAllPerms`） | 否则超管会被自己新建的权限体系锁死（这是最容易踩的坑，已用测试覆盖） |
| 强制机制 | **集中式"URL 前缀 → 权限码"映射**（`ApiPermGuard`），在 `SaTokenConfig` 拦截器内校验；**方法感知**：写必收口，读按"共享只读"白名单 | 469 端点逐个注解易漏、散落难审；集中表可一眼看全、便于"一控制器多页"的显式取舍；需同页细分时仍可叠加 `@SaCheckPermission` |
| 失败语义 | 新增 `NotPermissionException → 403「无权限访问」` | 此前未覆盖 ⇒ 会掉进兜底成为 500，前端无法区分"没权限"与"服务出错" |

### 10.16 前端导航全面审计 + 「点整理单后顶部导航只剩首页」修复（2026-09-19）

**发现路径**：用户使用新「退货整理」双页签时报告 —— 点「整理单」后顶部面包屑**只剩「首页」**。

**根因（两处独立缺陷，都在既有实现里，不是本次页签功能引入的）**：

| 编号 | 位置 | 缺陷 |
|---|---|---|
| **N-1** | `layout/index.vue` `breadcrumbItems` | 面包屑拿"当前激活页签地址"去匹配菜单 `routePath`（**纯路径**）。历史实现页签存的是 `route.fullPath`（**含 query**）⇒ 精确匹配 `path === routePath` 与前缀匹配 `path.startsWith(routePath + '/')` **双双失配** ⇒ `matched = null` ⇒ 直接 `return crumbs`，于是只剩「首页」 |
| **N-2** | `stores/tabs.ts` | 页签身份 = `route.fullPath` ⇒ 同一页每次 query 变化都**再开一个重复页签**（实测「模版管理」「研发立项」各出现 2 个），并进一步触发 N-1 |

**为什么长期没被发现**：只有"query 直接跟在菜单路径后"才中招 —— `/inventory/return-sort?tab=bills`、`/template?tab=contract`、`/dev/project?tab=active`；而 `/sale/return/add?saleOrderId=1` 这类"query 前还有子路径"的 URL 因 `startsWith('/sale/return/')` 仍命中，表现正常（同一批代码里既有坏样本也有好样本，掩盖了缺陷）。

**修复**：
1. `stores/tabs.ts`：页签身份改为 **query-free path**（新增 `normalizeTabPath()`）；新增 `Tab.fullPath` 记住"该页签最近一次访问的完整地址"，`switchTab()` 用它恢复页内状态（如 `?tab=bills`）；`loadTabs()` **自愈**旧 localStorage（按 query-free path 归并重复页签，用户无需手动清缓存）。
2. `layout/index.vue`：面包屑路径统一 `split('?')[0].split('#')[0]` 归一化；`openTab(route.path, title, route.fullPath)`；`closeTab` / `handleClosePage` 改按 `route.path` 判定并用 `tabTarget()` 回退（保留"恢复 query"能力）。
3. `views/inventory/return-sort/index.vue`：回到模版页 `views/template/index.vue` 的既定约定 —— `router.replace({ path: route.path, query })`（**必须显式给 path**）+ 反向 `watch(() => route.query.tab)`。

**审计资产升级（本轮主要交付）**：`ui-e2e-1-nav.ps1` 由"打开 63 页看有无报错"升级为**导航审计**，对**每个**菜单页断言：
- 面包屑 ≥ 2 级（首页 + 菜单链）；
- 页签栏**无重复标题**；
- 同页 + `?__probe=1` 的 query 变体，面包屑必须与无 query 时**完全一致**（即 N-1 的回归测试）；
